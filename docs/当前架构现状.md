# 当前架构现状

> 最后更新：2026-05-07

## 1. 当前真实模型
- 解析结果模型：`ParsedVideoInfo + List<VideoFormat>`
- 下载任务模型：单 `DownloadTask`
- 解析记录模型：`ParseRecord`
- 数据库版本：Room v3
- 当前主 UI 入口：`MainActivity -> RedesignNavHost`
- 播放组件：AndroidX Media3 / ExoPlayer（含 HLS）
- 抖音补充解析：App 内签名详情解析，不依赖本地 sidecar

## 2. 当前已落地能力
- 抖音、X、`kstore.vip/*.html#...` 链接解析
- 抖音图文、动图/实况图通过详情接口提取视频资源；动图类内容下载时只保存单个 `_动态.mp4`
- 抖音 Cookie 设置入口已接入我的页
- X 图文混合、多视频链接解析；同一视频多 m3u8 清晰度按推荐规则只保留一个展示项
- 普通 m3u8 与 `AES-128` 加密 m3u8 下载
- App 内 Media3/ExoPlayer 播放 m3u8/HLS 视频
- 解析结果页主展示 + 缩略选择；缩略区不触发播放
- 新 UI 主导航：下载工作台 / 资源库 / 信息中心
- 资源库三栏：进行中 / 已完成 / 解析记录，三栏切换按钮悬浮固定在底部导航上方
- 下载失败分段失败组重试；重试只重试当前集合内失败项
- 已完成集合只展示成功内容，失败项不再导致整个已完成集合判失败
- 已完成任务管理、删除、App 内图片查看与 App 内视频播放
- 已完成列表只展示封面，合集项显示合集标识
- X Cookie 设置入口与下载完成通知开关已接入“我的”页面
- sidecar 验证工具、Motion Photo/vivo 实况图实验代码已清理出运行时

## 3. 当前实现边界
- 批量下载不是 `TaskGroup + TaskItem`，而是循环创建多个 `DownloadTask`
- 下载失败分段的“任务组”由 `parseRecordId` 做 UI 分组，不是持久化任务组实体
- 当前没有帖子级多媒体结构，不支持 `ParsedPost / ParsedMediaItem / DownloadCandidate`
- 当前解析结果页仍基于旧模型驱动，随着多媒体需求增加会继续承压
- 解析记录页只持久化 `ParseRecord` 摘要，暂不能从历史记录直接恢复完整资源确认页
- 新 UI 的图集聚合仍是基于同一 `parseRecordId` 的 UI 聚合，不是数据库级任务组
- X 多媒体去重是在现有 `VideoFormat` 列表上做收敛，不等价于真正的帖子级媒体模型
- 抖音动图/实况图保存为 mp4 文件，不写入系统相册可识别的原生实况图格式
- `VideoFormat.pairedImageUrl` 只用于保留动态资源封面关系；当前不会额外生成封面文件

## 5. 维护建议
- 继续修当前问题时，默认以本文件和 `docs/技术设计文档.md` 为准
- 若要推进多媒体重构，先确认是否要正式引入帖子级解析模型与批量任务模型
- 在底层模型未升级前，不要把 UI 分组逻辑误认为稳定领域模型
- 临时目录 `tmp/`、临时截图、调试数据库、本机 `.claude/` 设置不入库；相关规则已写入 `.gitignore`
- 抖音问题优先检查 `DouyinSignedWebParserGateway`、`DouyinDetailMediaExtractor`、抖音 Cookie 和详情接口响应，不再排查本地 sidecar
